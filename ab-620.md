## Before you start

### 1. Standard (classic) experience vs the new experience

Copilot Studio now runs everything on a **harness**, and there are three: the **standard harness** (rule-based agents and agent flows, built from topics, tools, and knowledge), the **GitHub Copilot harness** (reasoning-heavy agents and workflows), and the **Copilot chat harness** (extending Microsoft 365 Copilot Chat). Most of the doc pages behind AB-620 objectives that I opened (agent flows, computer use, MCP, A2A, knowledge sources, evaluation, Application Insights, and more) carry a note that they describe features for the **standard harness**, and the AB-620 Microsoft Learn modules say they are based on the **classic experience**. Build your practice agents in the standard/classic experience so what you see matches the training.

### 🧠 Exam notes

- Authentication options: **No authentication**, **Authenticate with Microsoft**, and **Authenticate manually**. Authentication changes take effect only after you **publish**.
- **No authentication** means anyone with the link can chat, so the agent can only reach public information. The option isn't available when a data policy requires authentication.
- Per the authentication doc, **Teams + Microsoft 365 channels support only Authenticate with Microsoft**; choosing another option blocks those channels. Use **Authenticate manually** for other channels such as a website. **Authenticate with Microsoft** also isn't available for agents that integrate with Dynamics 365 Customer Service.
- Variables differ: with Authenticate with Microsoft you get `User.ID` and `User.DisplayName`; `User.AccessToken` and `User.IsLoggedIn` exist only with manual authentication.
- Manual providers: Entra ID V2 with federated credentials, with certificates, or with client secrets; Entra ID (V1); or any Generic OAuth 2 provider.
- **Require users to sign in** creates a read-only system topic, isn't available for the first two options, and can't be turned off when a data policy requires authentication. Agent sharing can control who in your organization may chat only with **Authenticate with Microsoft** or manual **Microsoft Entra ID** with sign-in required; with **No authentication** or **Generic OAuth 2**, anyone with access to the agent can chat.
- Microsoft's ALM guidance: dev and test as **sandbox** environments, production as a **production-type** environment, and an Entra security group limiting each environment's members.
- Some items are **not solution-aware** and need post-deployment steps: Application Insights settings, manual authentication settings, Direct Line / web channel security settings, deployed channels, and sharing.
- MCP servers are reached through Power Platform connectors, so **data policies that govern connectors also govern MCP tools**.
- Copilot connectors (formerly Microsoft Graph connectors) index content into Microsoft Graph; Power Platform connectors call APIs in real time. Many enterprises use both.
- Multi-agent isn't automatically better: it adds latency (extra orchestration hops) and increases the testing and governance surface.

### 🧠 Exam notes

- Agent flows are low-code automations built in Copilot Studio or Power Automate. Added as a **tool**, the agent's orchestrator can call them at runtime to fetch data or take action.
- **Request for information (RFI):** pauses the flow, collects input from designated people, and lets later steps use it. Requests go out via **Outlook only**. The docs say requests can't be sent to users outside your tenant. If you list several people, the **first response wins** and later ones aren't processed.
- RFI input types: **text, yes/no, email, number, date**. Inputs can be optional, have placeholder text, and text inputs can be single-select or multi-select.
- Known RFI issue: outputs can come back wrapped in double braces when an input name contains spaces, so **name inputs without spaces**.
- **Monitoring tabs:** *Overview* (details, connections, owners, recent runs, turn the flow off), *Activity* (run history and status, step through a run, **resubmit or cancel** multiple runs), *Analytics* (run counts, failure rate, trends).
- Analytics limits: runs can take up to about **30 minutes** to appear, run-analysis metrics are only for **solution** flows, and runs of co-owned or shared flows aren't counted.
- The agent flow pages are documented for the standard harness. The newer experience documents "workflows" on separate pages, so make sure you're reading the agent-flow pages when you study.
- *Numbers such as parameter type limits, response time windows, and payload sizes came up in secondary sources and are deliberately not listed here. Confirm them in the agent flow docs above before relying on them.*

4. An RFI action returns values wrapped in double curly braces. What is the likely cause and fix?

### 🧠 Exam notes

- **Generative orchestration** (the default for new standard-harness agents) selects topics, tools, child and connected agents, and knowledge mainly by their **descriptions** (plus names and parameters). **Classic orchestration** matches topics by **trigger phrases**, and tools can only be called explicitly from a topic.
- With generative orchestration, topic triggers show **The agent chooses** instead of **User says a phrase**. Overlapping descriptions make selection unpredictable, so make descriptions specific and say what a component *can't* do.
- Turning generative orchestration on for an old classic agent auto-generates topic descriptions from trigger phrases, which are often good enough but worth rewriting. An admin can disable generative orchestration in an environment.
- To avoid duplicate answers, let a topic return its result as an **output variable** (plus an answered-state output) instead of always writing a message.
- Useful nodes and triggers: **End all topics** cancels the orchestrator's remaining plan; triggers **AI response generated** and **Plan complete**; **Clear variable values** can clear the conversation history the planner uses. The **Reset Conversation** system topic does *not* clear that history.
- Known generative orchestration limits: the **Conversational boosting** system topic isn't used for knowledge search, custom entities (closed list, regex) aren't supported as tool/topic input parameters (use a Question node), and only limited conversation history is available.
- **OnKnowledgeRequested:** turns a topic into a custom knowledge source that contributes results to generative answers. It can only be configured in **code view (YAML)**. It exposes `System.SearchQuery`, `System.KeywordSearchQuery` (concatenate this onto your search URL because Copilot Studio rewrites the query with conversation context), and `System.SearchResults` (results shaped as Content, ContentLocation, Title).
- Custom knowledge limits: up to **15 snippets** total across all custom knowledge topics, which are invoked simultaneously when knowledge is needed.
- The generative answers node's settings covered by the Applied Skills study guide include content moderation level, response formatting, model selection, disabling ungrounded responses, and disabling web search.
- Adaptive cards can be authored in the designer or as JSON and can be dynamic with Power Fx. Rendering varies by channel, so test in your target channel.

### 🧠 Exam notes

- **MCP transport:** Copilot Studio supports the **Streamable** transport. **SSE** is deprecated and no longer supported for MCP after August 2025.
- **Two ways to add an MCP server:** the **MCP onboarding wizard** (recommended: name, description, URL, authentication) or a **custom connector** created from an OpenAPI schema that marks the operation with `x-ms-agentic-protocol: mcp-streamable-1.0`.
- **MCP authentication:** none, **API key** (sent in a header or a query parameter), or **OAuth 2.0** in three flavors: **dynamic discovery** (dynamic client registration with a discovery endpoint, simplest), **dynamic** (DCR but you supply endpoints), and **manual** (client ID, secret, authorization, token, and refresh URLs, plus optional scopes; a callback URL is shown to register with your identity provider). The server description matters because the orchestrator uses it to decide when to call the server.
- MCP access uses Power Platform connectors, so a **data policy** that governs connectors also governs the MCP server and its tools.
- **REST API tool (preview):** needs an **OpenAPI spec as JSON in v2 format** (a v3 spec is auto-converted), authentication (none, API key, or OAuth 2.0), and clear descriptions because the orchestrator uses them to choose the tool. You pick which operations to expose, and you can pick a solution (or one is created). Descriptions for parameters can't be blank.
- **Custom connector vs REST API tool:** a custom connector is a reusable Power Platform asset governed by data policies and usable beyond one agent; the REST API tool is a guided way to publish selected OpenAPI operations as agent tools.
- **Computer use** needs **generative orchestration** and runs on a **Windows** machine. Machine options: **hosted browser** (preview, quick start, not recommended for production, not joined to your tenant), **Cloud PC pool** (preview, Entra joined and Intune enrolled), or **bring your own machine** (Power Automate for desktop 2.61.132.25266 or later, registered, with **Enable for computer use** turned on). Runs on the same machine are **queued**.
- Computer use configuration: name, description, **model** (OpenAI CUA and Claude Sonnet 4.5 are GA; Sonnet 4.6 and Opus 4.6 are experimental, and Anthropic models need admin approval for external models), instructions (full URLs and exact app names, step by step), inputs, machine, connection, and credentials.
- Computer use credentials: **maker-provided** (default, suits autonomous agents, and sharing means users act with the author's access on that machine) or **end user credentials**. **Stored credentials** live in Power Platform internal storage or your **Azure Key Vault**. **Access control** lists allowed sites and apps but only blocks *acting* on others, and **Enforce HTTPS** blocks HTTP sites. **Human supervision** emails a reviewer through Outlook when harmful instructions are suspected.
- Computer use is best for **autonomous** agents. It bills **5 Copilot Credits per step** (15 for a premium model).
- **Monitoring computer use:** *Activity > run > Activity map or Transcript* (step-by-step reasoning and screenshots). Detailed logs go to **Dataverse** by default (verbosity: all data, data without screenshots, minimal; default retention 7 days) and can be sent to **Microsoft Purview** (activity term `CUAOperation`).
- Prefer an API or connector whenever one exists; computer use is for systems with no API.

### 🧠 Exam notes

- Ways to add agents: **child agents** (inside the parent), **other Copilot Studio agents in the same environment**, and external agents over **A2A**, **Microsoft Foundry (preview)**, **Fabric Data agents (preview)**, or **Microsoft 365 Agents SDK (preview)**. All appear on the main agent's **Agents** page.
- **Use child agents** when it's one use case managed by one team, you want to group tools, instructions, and knowledge, and you don't need separate settings, authentication, deployment, publishing, or reuse.
- **Split into connected agents** when routing quality degrades (a rule of thumb from the docs is more than **30-40 choices** of tools, topics, and agents, or similar descriptions), when different teams own agents, when agents need their own model, channels, or ALM, or when you want reuse.
- Multi-agent costs: extra orchestration hops raise **latency**, and testing, management, and governance surface grows. Child and connected agents follow the main agent's **Use general knowledge** setting.
- You can **redirect** to a child or connected agent from a topic (the topic resumes afterward) and reference agents from the instructions with `/`. You can toggle an agent **Enabled** or disconnect it.
- Limits: **Fabric Data agents** can't be a Redirect target, can't be referenced in instructions, and don't work when the main agent is deployed to **Microsoft 365 Copilot**. An agent that has connected agents can't also serve as a connected agent for a second main agent. Citations may not survive being passed back.
- **A2A:** an open standard for agent-to-agent tasks that supports multi-turn interactions and rich metadata (unlike a plain HTTP connector). Enter the agent's **communication endpoint URL, not the agent card URL**. Copilot Studio reads the card from the standard `.well-known` location (`/.well-known/agent.json`) to pre-fill name and description. Authentication: **None, API key, or OAuth 2.0**. Requests carry a `contextId` and the full chat history in metadata.
- A2A connections use the **custom connector** infrastructure, so on-premises or virtual-network agents can be reached.
- **Which protocol when:** A2A for agents from other frameworks; MCP for tools and resources; custom connectors or HTTP tools for plain APIs; the Activity protocol for Microsoft 365 Agents SDK agents.
- **Foundry agents:** connect from *Add agent > Connect to an external agent > Microsoft Foundry* using the project endpoint URL, then a name, description, and **Agent ID**. Only agents from the **new Foundry portal** work (the old portal gives `404 - Version not found`). The Foundry agent must have the **Activity protocol** endpoint enabled, which today is done only through the REST API or Python SDK; otherwise you get a 400 at runtime.
- **Fabric data agents:** choose *Microsoft Fabric* under external agents, pick the connection and the data agent, and sharpen the description if it overlaps other tools.
- Connecting Foundry, Fabric, and Agents SDK agents is **preview**, so re-verify status before your exam.

### 🧠 Exam notes

- **Test sets:** a single-response test set holds up to **100 test cases**. Create them with a **quick question set** (10 questions generated from the agent's description, instructions, and capabilities), a **full question set** (generated from knowledge sources or topics, with a number you choose), your **test chat**, **importing** a CSV or text file, writing them by hand, or from **themes** (analytics). Knowledge-based generation suits generative orchestration; the *Topics* option suits classic orchestration.
- Import files: columns `Question` then `Expected response`, up to 100 questions, each up to 1,000 characters. Generating from files works with individual files up to 5 MB (SharePoint folders aren't supported).
- **Evaluation methods:**
  - *General quality*: LLM-graded on relevance, groundedness, completeness, and abstention, needs no expected answer, and is on every test set by default. An appropriate refusal can be flagged, so use a **custom** method to treat a correct refusal as a pass.
  - *Content safety*: pass or fail by severity threshold (0 is strictest, 7 most permissive) per content type.
  - *Compare meaning*: meaning similarity against an expected answer (default pass score 50).
  - *Tool use*: whether expected tools or topics were used (single response).
  - *Keyword match*: any or all expected keywords.
  - *Text similarity*: cosine similarity of wording, scored 0 to 1.
  - *Exact match*: character for character.
  - *Custom*: your own evaluation instructions and labels, each marked pass or fail.
- A method that needs expected answers or keywords gives an **Invalid** result for any test case missing them. You can combine multiple methods in one test set. Conversation (multi-turn) test sets support only a subset of methods.
- **Results** stay in Copilot Studio for **89 days**, so export to CSV to keep them. Automated testing uses the **test account** you select, so its access to knowledge and tools shapes the results, and any maker with access to the agent can see its test sets.
- **ALM golden rules:** don't customize outside dev, always work in solutions, use a **custom publisher and prefix**, create separate solutions only to deploy components independently, use **environment variables** for settings and secrets that differ per environment, export and deploy as **managed** (unmanaged only in dev), and consider automating.
- **Environments:** at least dev, test, and production, with production as a production-type environment and the rest sandbox, each limited by an Entra security group.
- **Solution-aware exceptions** needing manual steps after deployment: Application Insights settings, manual authentication settings, Direct Line / web channel security settings, deployed channels, and sharing.
- **Component collections** package reusable topics, knowledge, actions, and entities and can move between environments in solutions.
- **ALM tools:** **Azure DevOps** (enterprise CI/CD and source control), **GitHub Actions for Power Platform** (dev and admin teams), and **pipelines in Power Platform** (built in, low setup, aimed at citizen developers, centralized deployment visibility).
- **Extending pipelines:** the documented pattern uses three environments (**pipeline host**, **development**, **target**), triggers a flow on a deployment request for a solution containing an agent, pauses the deployment, runs automated tests with the Copilot Agent Kit, and decides whether to continue based on results.
- Using an **Azure Key Vault** secret as an environment variable needs the **PowerPlatform resource provider** registered in the subscription and permissions on the vault.

## Quick reference cheat sheet

### Which integration option?

| Situation | Best fit |
| --- | --- |
| A prebuilt Power Platform connector exists | Connector tool |
| You have an OpenAPI definition and want a reusable, data-policy-governed asset | Custom connector |
| You have an OpenAPI spec (JSON, v2) and want selected operations as tools in this agent | REST API tool (preview) |
| One-off call inside a single topic | Send HTTP request node |
| The vendor exposes an MCP server | MCP tool through the onboarding wizard (Streamable transport) |
| No API at all, only a UI | Computer use (Windows machine, generative orchestration) |
| Multi-step, deterministic business process, possibly with a human step | Agent flow |
| Another agent built on an external framework | A2A connection |
| Agent built with the Microsoft 365 Agents SDK | Activity protocol connection (preview) |
| Agent built in Foundry (new portal) | Connected Foundry agent, with the Activity endpoint enabled (preview) |
| Natural-language questions over Fabric data | Fabric data agent (preview; not a Redirect target) |
| Group related tools and knowledge inside your own agent | Child agent |
| Another team's published Copilot Studio agent | Connected agent |
| Your own search API as grounding | Topic with the `OnKnowledgeRequested` trigger (code view) |

### Which knowledge option?

| Need | Best fit |
| --- | --- |
| Index non-Microsoft content (ServiceNow KB, Jira, wikis) into Microsoft Graph with citations | Copilot connector |
| Live data or transactions with no data copied | Power Platform connector as real-time knowledge (preview) or as a tool |
| Large document sets with your own chunking, embeddings, and semantic ranking | Azure AI Search vector index through a data connection |
| Ground with a search endpoint you control | `OnKnowledgeRequested` custom knowledge topic (max 15 snippets combined) |

### Numbers worth memorizing

| Fact | Value |
| --- | --- |
| Passing score | 700 or greater |
| Domain weights | 30-35% / 40-45% / 20-25% |
| Test cases per single-response test set | 100 (import file: 100 questions, 1,000 characters each) |
| Quick question set size | 10 questions |
| Files for test generation | Up to 5 MB, individual SharePoint files only |
| Evaluation results retention | 89 days (export to CSV) |
| Compare meaning default pass score | 50 |
| Content safety threshold scale | 0 (strictest) to 7 (most permissive) |
| Custom knowledge snippets used per answer | Up to 15 across all custom knowledge topics |
| Routing degrades around | More than 30-40 tools, topics, and agents on one agent (rule of thumb) |
| Computer use billing | 5 Copilot Credits per step (15 for a premium model) |
| Computer use Dataverse log retention | 7 days by default |
| Agent flow analytics delay | Up to about 30 minutes |
| RFI response used | First person to respond |

### Authentication options

| Option | Notes |
| --- | --- |
| No authentication | Anyone with the link can chat; public information only; unavailable if a data policy requires authentication |
| Authenticate with Microsoft | Only option supported by Teams + Microsoft 365 channels; `User.ID` and `User.DisplayName` available; not for Dynamics 365 Customer Service handoff |
| Authenticate manually | Entra ID V2 (federated credentials, certificates, or secrets), Entra ID, or Generic OAuth 2; adds `User.AccessToken` and `User.IsLoggedIn`; needed for other channels such as a website |

### Child agent vs connected agent

| | Child agent | Connected agent |
| --- | --- | --- |
| Where it lives | Inside the parent agent | Separate agent (published) |
| Own settings, auth, deployment, ALM | No | Yes |
| Reusable by other agents | No | Yes |
| Typical owner | Same team | Different teams |
| Extra orchestration hop | Yes | Yes |
